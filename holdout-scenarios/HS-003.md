# HS-003 — Security audit discovers actual SSRF vulnerability

## Description

A user connects to an MCP server that exposes a tool called `fetch_url` which
accepts an arbitrary URL parameter. When invoked, the server makes an HTTP request
to the provided URL and returns the response body. This is a classic Server-Side
Request Forgery (SSRF) vector. The tool's response includes evidence of a redirect
to the cloud metadata endpoint `169.254.169.254`, which would allow an attacker to
steal cloud credentials.

Forge MCP's security audit must detect this SSRF pattern with high confidence,
correctly classify it under the appropriate attack surface taxonomy (AST03: tool
input manipulation, AST06: exfiltration via tool responses), and produce actionable
findings.

## Setup

1. Create a mock MCP server with the following tool:
   ```json
   {
     "name": "fetch_url",
     "description": "Fetch content from any URL",
     "inputSchema": {
       "type": "object",
       "properties": {
         "url": { "type": "string", "description": "URL to fetch" }
       },
       "required": ["url"]
     }
   }
   ```
2. Configure the mock server so that calling `fetch_url` with
   `url=http://169.254.169.254/latest/meta-data/` returns:
   ```json
   {
     "content": [
       {
         "type": "text",
         "text": "ami-id\nami-launch-index\nami-manifest-path\nhostname\ninstance-id\nlocal-ipv4\npublic-ipv4\nsecurity-credentials/"
       }
     ]
   }
   ```
3. Connect Forge MCP to the mock server

## Steps

1. Run `forge-mcp connect test-server`
2. Run `forge-mcp audit test-server --json`
3. Examine the JSON output for SSRF-related findings
4. Verify finding severity, confidence, and attack surface classification
5. Run `forge-mcp audit test-server` (human-readable output)
6. Verify the human-readable report explains the risk clearly

## Expected Behavior

- Security audit completes without errors
- At least one finding is produced with:
  - **Category:** SSRF or arbitrary URL fetch
  - **Severity:** High or Critical
  - **Confidence:** High (≥ 0.8)
  - **Attack surface:** Maps to AST03 (tool input manipulation) and/or AST06 (exfiltration)
  - **Tool:** `fetch_url` identified as the vulnerable tool
  - **Evidence:** References the `url` parameter accepting arbitrary input
- The finding includes a remediation suggestion (e.g., URL allowlisting, blocking private IPs)
- Human-readable output explains WHY this is dangerous (cloud credential theft)
- JSON output is machine-parseable for integration with CI/CD pipelines
- Exit code is non-zero (indicating findings were discovered)

## Must-Pass Criteria

1. SSRF vulnerability is detected (not missed — zero false negatives for this pattern)
2. Finding severity is High or Critical (not Medium or Low)
3. The specific tool `fetch_url` is identified in the finding
4. Attack surface taxonomy mapping is present (AST03 and/or AST06)
5. Exit code is non-zero when security findings exist

## Satisfaction Scoring Rubric

| Criterion | 0 | 1 | 2 | 3 |
|-----------|---|---|---|---|
| SSRF detection | Not detected | Detected as low/info severity | Detected as medium severity | Detected as high/critical with correct classification |
| Tool attribution | No tool identified | Wrong tool identified | Correct tool, missing parameter detail | Correct tool + `url` parameter identified |
| Attack surface mapping | No AST mapping | Partial mapping (1 of 2) | Both AST03 + AST06 mapped, minor issues | Both mapped with clear explanation |
| Remediation quality | No remediation | Generic "fix it" advice | Specific but incomplete suggestion | Actionable: URL allowlist, private IP blocking |
| Output quality | Unparseable / crashes | Parseable but missing fields | Complete JSON + readable output | Rich JSON + clear human explanation of risk |
