# HS-014 — Security finding suppression and re-classification

## Description

A developer runs a security audit on an MCP server, discovers an SSRF finding
classified at medium severity, and suppresses it (accepts the risk). Later, a rule
update changes the SSRF classification from medium to critical severity. The old
suppression should remain valid for the originally suppressed finding instance, but
new occurrences of the same pattern must NOT be auto-suppressed — they should appear
as new critical findings.

This tests the suppression system's integrity: suppressions are instance-specific, not
pattern-blanket, and severity re-classification does not silently inherit old
suppression decisions.

## Setup

1. Create a mock MCP server "api-server" with a tool that has an SSRF-susceptible pattern:
   ```json
   {
     "name": "proxy_request",
     "description": "Forward HTTP request to internal service",
     "inputSchema": {
       "type": "object",
       "properties": {
         "url": { "type": "string" },
         "method": { "type": "string" }
       },
       "required": ["url"]
     }
   }
   ```
2. Run initial audit and get a finding at medium severity
3. Suppress the finding with reason: "accepted risk — URL is validated in proxy layer"

## Steps

1. Run `forge-mcp connect api-server`
2. Run `forge-mcp audit api-server --json` — note the finding ID and severity (medium)
3. Suppress the finding:
   ```bash
   forge-mcp suppress <finding-id> --reason "accepted risk — URL validated in proxy layer"
   ```
4. Run `forge-mcp audit api-server --json` — verify finding no longer appears (suppressed)
5. Simulate a rule update that reclassifies SSRF from medium → critical:
   - Update the rule definition or configuration
6. Run `forge-mcp audit api-server --json` — after rule update
7. Check whether the original suppressed finding stays suppressed
8. Add a second tool with the same SSRF pattern to the server:
   ```json
   {
     "name": "fetch_external",
     "description": "Fetch content from external URL",
     "inputSchema": {
       "type": "object",
       "properties": { "url": { "type": "string" } },
       "required": ["url"]
     }
   }
   ```
9. Run `forge-mcp audit api-server --json` — check for new finding
10. Verify the new finding is NOT suppressed and is at critical severity

## Expected Behavior

- **Step 2:** Initial audit finds SSRF on `proxy_request` at medium severity
- **Step 3:** Suppression succeeds, finding marked as suppressed with reason
- **Step 4:** Re-audit shows the finding is suppressed (hidden from default view,
  or shown with "suppressed" indicator)
- **Step 6:** After rule update:
  - The originally suppressed finding STAYS suppressed (suppression is instance-bound)
  - The suppression metadata may show "note: severity reclassified from medium to critical"
- **Step 9-10:** New SSRF finding on `fetch_external`:
  - Appears as a NEW finding (not auto-suppressed)
  - Classified at critical severity (new rule classification)
  - Has its own finding ID (distinct from the suppressed one)
- Suppression history is auditable:
  - Who suppressed, when, with what reason
  - Severity at time of suppression vs current severity

## Must-Pass Criteria

1. Original finding stays suppressed after rule reclassification
2. New occurrence of same pattern is NOT auto-suppressed
3. New finding uses the updated severity (critical, not medium)
4. Suppression metadata is preserved and auditable
5. Clear distinction between "suppressed instance" and "new occurrence"

## Satisfaction Scoring Rubric

| Criterion | 0 | 1 | 2 | 3 |
|-----------|---|---|---|---|
| Suppression persistence | Suppression lost on re-audit | Suppression intermittent | Suppression persists, no reclassification note | Persists + notes severity change |
| New occurrence handling | New finding auto-suppressed | New finding at old severity | New finding at new severity, no distinction | New finding at critical, clearly marked as new |
| Severity reclassification | No effect on findings | All findings reclassified (breaks suppression) | New findings reclassified, old unchanged | Clean separation: old suppressed, new at critical |
| Audit trail | No history | Suppression exists but no details | Who/when/reason recorded | Full history: who/when/reason/original-severity |
| Instance isolation | Pattern-blanket suppression | Partial isolation | Instance-bound, minor leaks | Perfect instance isolation, verifiable |
