# HS-012 — Cross-platform daemon lifecycle

## Description

A developer starts the Forge MCP daemon, connects to a server, then kills the daemon
process (simulating a crash or machine restart). They then restart the daemon. The
system must handle this lifecycle cleanly: stale lock files must be cleaned up,
sessions must be re-establishable, and previously connected servers should be
reconnectable without manual configuration.

This tests daemon robustness across the start → crash → restart cycle, which is a
common real-world scenario (ASM-005: users expect daemon reliability).

## Setup

1. Configure one MCP server "test-server" in any editor config
2. Start the mock MCP server process
3. Ensure the daemon lock file path is known (e.g., `~/.forge-mcp/daemon.lock` or
   platform-appropriate location)

## Steps

1. Start the daemon: `forge-mcp daemon start`
2. Verify daemon is running: `forge-mcp daemon status`
3. Connect to server: `forge-mcp connect test-server`
4. Verify connection: `forge-mcp info test-server` (should list tools)
5. Record the daemon PID
6. Kill the daemon: `kill -9 <daemon-pid>`
7. Verify lock file exists (stale)
8. Attempt to start daemon again: `forge-mcp daemon start`
9. Verify daemon starts successfully (stale lock cleaned up)
10. Verify daemon status: `forge-mcp daemon status`
11. Reconnect to server: `forge-mcp connect test-server`
12. Verify connection works: `forge-mcp info test-server`

## Expected Behavior

- **Step 1-4:** Normal daemon lifecycle — start, connect, inspect all work
- **Step 6:** Daemon process dies, leaving a stale lock file
- **Step 8:** Daemon restart succeeds because:
  - Forge MCP detects the stale lock file
  - Validates that the PID in the lock file is no longer running
  - Removes the stale lock file
  - Creates a new lock file with the new PID
  - Starts the daemon normally
- **Step 8 alternative:** If the lock file PID is still somehow valid (race condition),
  Forge MCP reports "daemon already running" with the PID
- **Step 11-12:** Reconnection to the server succeeds:
  - Previous session state may be lost (acceptable)
  - New connection is established cleanly
  - Server responds to queries normally
- Lock file is platform-appropriate:
  - Unix: file with PID, advisory lock
  - Windows: named mutex or PID file
- Daemon logs the crash recovery in its log file

## Must-Pass Criteria

1. Stale lock file does not prevent daemon restart
2. Daemon starts successfully after crash (stale lock cleaned)
3. Server reconnection works after daemon restart
4. No orphaned resources (sockets, temp files) from the crashed daemon
5. Daemon status command accurately reports state after restart

## Satisfaction Scoring Rubric

| Criterion | 0 | 1 | 2 | 3 |
|-----------|---|---|---|---|
| Stale lock handling | Can't start, "already running" | Requires manual lock deletion | Auto-cleans after user confirmation | Auto-detects stale, cleans silently with log |
| Restart reliability | Daemon won't start | Starts but requires config redo | Starts cleanly, loses connection info | Starts cleanly, remembers last config |
| Reconnection | Can't reconnect, errors | Reconnects with manual commands | Reconnects but session state messy | Clean reconnection, new session established |
| Resource cleanup | Orphaned sockets/files | Some cleanup, minor leaks | Full cleanup, minor temp file remnants | Complete cleanup, verified via lsof/netstat |
| Status accuracy | Status wrong after restart | Status correct after delay | Status correct immediately | Status correct + shows crash recovery info |
