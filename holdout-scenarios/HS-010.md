# HS-010 — Sampling proxy failure with graceful degradation

## Description

An MCP server requests Forge MCP to create an LLM completion on its behalf via the
`sampling/createMessage` protocol method. Forge MCP acts as the sampling proxy,
forwarding the request to a configured LLM API. However, the LLM API returns a
429 (rate limit exceeded) response. Forge MCP must handle this failure gracefully —
returning a structured error to the server, logging the failure in the TUI, and
allowing the server to continue functioning with reduced capability.

This tests the sampling proxy's error handling path and validates that LLM API
failures don't cascade into server disconnection (ASM-013).

## Setup

1. Create a mock MCP server that:
   - Initializes successfully with `sampling` in client capabilities
   - After initialization, sends a `sampling/createMessage` request:
     ```json
     {
       "method": "sampling/createMessage",
       "params": {
         "messages": [
           { "role": "user", "content": { "type": "text", "text": "Summarize this code" } }
         ],
         "maxTokens": 100
       }
     }
     ```
   - On receiving an error response, continues operating (responds to `tools/list`, etc.)
2. Configure Forge MCP's LLM proxy to point to a mock LLM endpoint that returns:
   ```http
   HTTP/1.1 429 Too Many Requests
   Retry-After: 60
   {"error": {"message": "Rate limit exceeded", "type": "rate_limit_error"}}
   ```
3. Launch `forge-mcp tui` and connect to the server

## Steps

1. Connect to the mock server via TUI
2. Observe the sampling request being sent by the server
3. Verify Forge MCP forwards to the LLM proxy
4. Observe the 429 error handling
5. Check TUI traffic panel for the error log entry
6. Verify the server receives a structured error response
7. Run `forge-mcp info test-server` to verify server is still connected and responsive
8. Invoke a tool on the server to verify it still works

## Expected Behavior

- Forge MCP receives the `sampling/createMessage` request from the server
- Forge MCP forwards the request to the configured LLM endpoint
- On receiving 429, Forge MCP:
  - Does NOT disconnect from the server
  - Does NOT crash or panic
  - Returns a JSON-RPC error to the server with:
    - Appropriate error code (e.g., -32000 or similar server error)
    - Message indicating rate limit / temporary failure
    - Optional: Retry-After hint from upstream
  - Logs the failure in the TUI traffic panel with:
    - Timestamp
    - Direction indicator (proxy → LLM failed)
    - Error details (429, rate limit)
- The server continues operating — subsequent `tools/list` and `tools/call` work normally
- The TUI connection status remains "connected"
- No data loss or corruption from the failed sampling request

## Must-Pass Criteria

1. Server connection survives the LLM proxy failure (not disconnected)
2. Server receives a structured JSON-RPC error response (not a hang or timeout)
3. TUI displays the error in the traffic log
4. Subsequent server operations (tools/list, tools/call) work normally
5. Forge MCP process does not crash

## Satisfaction Scoring Rubric

| Criterion | 0 | 1 | 2 | 3 |
|-----------|---|---|---|---|
| Connection resilience | Server disconnected on error | Server stays connected, unstable | Server connected, minor state issues | Server fully functional, clean state |
| Error response quality | No response / hang | Generic error, no details | Structured error with code + message | Structured error + rate limit details + retry hint |
| TUI logging | No log entry | Error in debug log only | Error in traffic panel, minimal detail | Clear traffic entry with timestamp + error details |
| Continued operation | Tools broken after error | Tools work after retry/delay | Tools work immediately, minor warnings | Tools work immediately, no trace of prior error |
| Proxy transparency | Opaque failure, no visibility | Error code only | Error with upstream details | Full proxy chain visibility (request → upstream → error → response) |
