| R-001 | **Anthropic releases comprehensive official CLI/TUI tool.** Anthropic owns the protocol and has distribution advantage (SDK + Claude ecosystem). A full official tool would significantly erode Forge MCP's adoption. | business | Medium | HIGH | open | Focus on capabilities Anthropic is unlikely to prioritize: runtime security auditing, enterprise compliance reporting. Establish community adoption before this happens. Monitor MCP roadmap announcements. NFR candidate: no. Security focus: no. | Market intel R-1 |
| R-002 | **MCP spec breaking changes.** Domain research confirms faster-than-expected spec cadence: 2024-11-05 → 2025-03-26 → 2025-06-18 (~6 months between updates, not 12). New capabilities (tasks, elicitation) add significant surface area. A new spec version could invalidate the conformance suite or break assumptions. | reliability | Medium-High | HIGH | open | Version-tag conformance suites. Support multiple spec versions simultaneously. Track spec repository for RFC/breaking-change proposals. Decouple spec version from binary version. Leverage rmcp for absorbing spec changes. NFR candidate: yes (spec version abstraction). Security focus: no. | CAP-019, ASM-007 |
| R-003 | **rmcp crate maintenance risk.** Domain research confirms rmcp is hosted at `warpdotdev/rmcp` (by Warp, not Anthropic directly). Hard dependency means inheriting bugs, gaps, or maintenance delays. rmcp API surface includes `ClientCapabilitiesBuilder`, `ServerCapabilities`, transport builders — substantial surface to depend on. | reliability | Medium | MEDIUM | open | Monitor rmcp release cadence and maintainer activity. Contribute upstream fixes. Define a thin interface boundary so protocol-level patches can supplement rmcp without forking. Assess rmcp bus factor during architecture phase. Note: rmcp is community-maintained, not Anthropic-maintained — different risk profile than "official SDK." NFR candidate: yes (interface abstraction layer). Security focus: no. | CAP-002, ASM-001, DI-004 |
| R-004 | **Security auditing false positives erode trust.** Runtime behavioral analysis is inherently heuristic. However, domain research reveals substantial deterministic detection opportunities: SSRF to known metadata IPs (169.254.169.254), RFC1918 private IP targeting, known-dangerous tool names. The risk is primarily in behavioral/pattern heuristics, not deterministic rules. | security | Medium | HIGH | open | Start with deterministic rules (high-precision): metadata IP detection, known-dangerous patterns. Layer heuristic rules with lower default confidence scores. Provide confidence scores on all findings. Allow user-defined suppression rules. Leverage BlueRock's published research for rule development. Track precision/recall per release. NFR candidate: yes (precision > 80%). Security focus: yes. | CAP-016, CAP-018, ASM-008 |
| R-005 | **TUI rendering performance at high message rates.** ratatui under heavy load (100+ events/sec) may not sustain 60fps with < 5MB RSS, especially on large terminal sizes. TUI is the signature differentiator. | performance | Medium | HIGH | open | Benchmark early against synthetic load. Implement frame-rate throttling (30fps fallback). Virtual scrolling for large datasets. Profile ratatui rendering hot paths. Consider differential rendering (only update changed cells). NFR candidate: yes (60fps at 100 events/sec, < 5MB RSS). Security focus: no. | CAP-006, CAP-008, ASM-004 |
| R-006 | **Editor config format instability.** Claude Desktop, Cursor, VS Code, and Windsurf may change their MCP config file formats without notice, breaking Forge MCP's parsers. | reliability | Medium | MEDIUM | open | Defensive parsing with version detection. Monitor editor release notes quarterly. Implement graceful degradation: if a config can't be parsed, skip it and report clearly rather than crashing. Maintain config format changelog. NFR candidate: no. Security focus: no. | CAP-001, ASM-002, DEC-008 |
| R-007 | **Open-source sustainability.** As a BOHICA-LABS project, long-term maintenance depends on adoption or monetization. Without either, the project risks abandonment. | business | Medium | MEDIUM | open | Plan enterprise features (security reports, compliance dashboards, team config management) as monetization lever. Establish community contributor pipeline. Keep core architecture simple enough for community contributions. NFR candidate: no. Security focus: no. | Market intel R-7 |
| R-008 | **IDE-native MCP debugging captures DevEx segment.** VS Code, Cursor, Windsurf add built-in MCP debugging panels, eroding the DevEx engineer persona's need for Forge MCP. | business | Medium | MEDIUM | open | Accept this risk for the DevEx segment. NFR candidate: no. Security focus: no. | Market intel R-5 |
| R-009 | **Cross-platform daemon behavior inconsistency.** The daemon architecture (lazy start, idle timeout, socket management) may behave differently on Linux, macOS, and Windows, especially around process lifecycle and signal handling. | reliability | Medium | MEDIUM | open | Test daemon lifecycle on all 5 target platforms. Use platform-abstracted process management. Implement explicit daemon health check and recovery. Provide fallback mode without daemon (cold-start per invocation). NFR candidate: no. | R-010 | **Unbounded traffic capture memory growth.** Long-running sessions with high-throughput servers could accumulate unbounded traffic captures, leading to OOM. | performance | Medium | HIGH | open | Implement configurable capture buffer limits (time-based and count-based). Security focus: no. | CAP-009, FM-012, DEC-011 |
| R-011 | **OWASP AST10 coverage metric achievability.** The brief targets ≥ 80% of OWASP AST10 risk categories covered. Domain research confirms the 10 AST10 categories: AST01 Malicious Skills, AST02 Supply Chain Compromise, AST03 Over-Privileged Skills, AST04 Insecure Metadata, AST05 Unsafe Deserialization, AST06 Weak Isolation, AST07 Update Drift, AST08 Poor Scanning, AST09 No Governance, AST10 Cross-Platform Reuse. Several of these (AST07 Update Drift, AST08 Poor Scanning, AST09 No Governance, AST10 Cross-Platform Reuse) address organizational/process concerns, not runtime behavior. | security | Medium | MEDIUM | open | Map each AST10 category to runtime-detectable vs. process/organizational. Runtime-addressable: AST01 (via behavioral analysis), AST02 (via supply chain signals in traffic), AST03 (via permission analysis), AST04 (via metadata inspection), AST05 (via deserialization pattern detection), AST06 (via isolation boundary checking). Process-only: AST07, AST08, AST09, AST10. Adjust target to "80% of runtime-applicable categories" (≥5 of 6 = 83%). Security focus: yes. | CAP-016, CAP-017, Market intel R-8 |
| R-012 | **"MCP is Dead" narrative reduces market.** Some voices argue CLI tools are better than MCP for agent consumption (7–32x cost advantage). If this view wins broadly, MCP server deployment slows and Forge MCP's TAM shrinks. | business | Low | HIGH | open | This debate is about agent consumption patterns, not server deployment. 10,000+ existing MCP servers need tooling regardless. Security focus: no. | Market intel R-6 |
| R-013 | **Client capability implementation complexity.** Domain research reveals that sampling, elicitation, and roots are **client capabilities** requiring Forge MCP to act as a responder to server-initiated requests. Sampling requires LLM API proxy integration (with tool calling support). Elicitation requires TUI/CLI user interaction flows for form and URL modes. These add significant implementation surface beyond the original "invoke server methods" mental model. | reliability | Medium | HIGH | open | Implement incrementally: roots first (simplest — filesystem boundary listing), then sampling proxy (most value — enables full protocol coverage), then elicitation (most complex — requires TUI interaction flow). Define clean handler interfaces via rmcp's `ClientCapabilitiesBuilder`. Ensure each handler has graceful fallback when not configured (DEC-016, DEC-017). NFR candidate: yes (all 10 spec capabilities covered). Security focus: no. | CAP-004, CAP-005, ASM-013, DI-016, DI-017 |
