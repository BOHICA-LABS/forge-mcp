# ADV-P2-003 — Schema-drift coverage still disagrees on whether annotations are part of the contract

- **Severity:** MEDIUM
- **Category:** contradiction
- **Location:** `.factory/specs/behavioral-contracts/BC-7.16.003.md`, `.factory/specs/verification-properties/vp-011-schema-drift-detection.md`, `.factory/specs/architecture/api-surface.md`

## Description

Pass 1’s schema-drift area is still internally inconsistent. One layer says tool annotations are part of detectable metadata, another says canonical hashing excludes them, and the VP insists annotation mutations must always produce findings. That is a direct traceability contradiction between L3, L4, and architecture API assumptions.

## Evidence

- `BC-7.16.003` summary says metadata includes “name, description, inputSchema, annotations” and `EC-009` says annotation changes produce an info-level finding.
- But the same BC’s `POST-002` and hash computation block define canonical metadata as only `name`, `description`, and `inputSchema`.
- `vp-011-schema-drift-detection.md` includes `ChangeAnnotation` in the mutation set and requires **any** such change to produce a non-empty finding set.
- `api-surface.md` defines `detect_schema_drift(prev, current)` over `ToolSet`, but never states whether annotations are part of the compared representation.

## Proposed Fix

Choose one rule and propagate it consistently:
- **If annotations are security-relevant:** include them in canonical metadata/hash definition, API docs, BC postconditions, and examples.
- **If they are auxiliary only:** remove annotation mutations from VP-011 and remove/soften `EC-009`.

Right now the spec promises both behaviors at once.
