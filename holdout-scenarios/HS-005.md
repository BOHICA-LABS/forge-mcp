# HS-005 — Performance under high message volume (1000+ msg/sec)

## Description

A developer connects to an MCP server that produces rapid-fire notification messages
(e.g., a logging/monitoring server emitting structured log entries). The message rate
exceeds 1000 messages per second. The TUI traffic inspector must remain usable — it
should throttle the display to maintain at least 30fps rendering while continuing to
capture all messages in a background buffer. The system must not run out of memory
even under sustained high-volume traffic.

This tests performance under adversarial message volume (R-005) and validates
non-functional requirements for TUI responsiveness and memory management.

## Setup

1. Create a mock MCP server that, after initialization, sends `notifications/message`
   at a rate of 1500 messages/second (exceeding the 1000/sec threshold)
2. Each message payload is ~200 bytes (realistic structured log entry)
3. Configure memory monitoring on the Forge MCP process (RSS tracking)
4. Launch `forge-mcp tui` and connect to the high-volume server
5. Let traffic flow for 60 seconds (total: ~90,000 messages, ~18MB raw)

## Steps

1. Open TUI, connect to high-volume server
2. Navigate to traffic inspection panel
3. Observe rendering frame rate during sustained traffic (measure with timing)
4. Attempt to scroll back through captured messages during live traffic
5. Attempt to select and inspect a specific message's detail view
6. Attempt to use keyboard shortcuts (filter, search, panel switch)
7. After 60 seconds, check process memory (RSS)
8. Stop the server, verify all captured messages are accessible
9. Search/filter through the captured buffer

## Expected Behavior

- TUI renders at ≥ 30fps throughout the test (no perceptible lag or freezing)
- Traffic inspector shows a throttled/sampled view during high-volume periods
  - Indicator shows "capturing: 1500 msg/s, displaying: ~30 msg/s" or similar
- Background capture continues at full rate
- Scrollback through captured messages works (may show "loading" for large buffers)
- Message detail inspection works for any selected message
- All keyboard shortcuts respond within 100ms
- Process RSS stays below 500MB after 60 seconds of sustained traffic
- After stopping traffic, full capture buffer is searchable/filterable
- Capture buffer implements eviction or disk spill for sustained loads (no OOM)

## Must-Pass Criteria

1. TUI does not crash or become unresponsive during 1000+ msg/sec traffic
2. Frame rate stays ≥ 30fps (no visible rendering stutter)
3. Process memory does not exceed 500MB after 60 seconds
4. Keyboard shortcuts remain responsive (< 200ms latency) during high traffic
5. Captured messages are accessible after traffic stops

## Satisfaction Scoring Rubric

| Criterion | 0 | 1 | 2 | 3 |
|-----------|---|---|---|---|
| Rendering performance | TUI freezes or < 10fps | 10-20fps with visible stutter | 20-30fps, occasional frame drops | ≥ 30fps sustained, smooth rendering |
| Memory management | OOM or > 1GB | 500MB-1GB, no eviction | < 500MB with eviction, minor leaks | < 200MB with clean eviction/spill |
| Capture completeness | Drops > 50% of messages | Captures 50-80% | Captures 80-99% | Captures 100%, buffer fully searchable |
| Throttle indication | No indication of throttling | Shows throttled but no rates | Shows capture rate, not display rate | Shows both capture and display rates clearly |
| Input responsiveness | Keys unresponsive (> 1s) | 500ms-1s latency | 200-500ms latency | < 100ms latency during high traffic |
