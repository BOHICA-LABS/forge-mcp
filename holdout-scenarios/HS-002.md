# HS-002 — Server crash during TUI traffic inspection

## Description

A developer is using the Forge MCP TUI to watch live JSON-RPC traffic between
their editor and an MCP server. While actively inspecting message payloads, the
MCP server process is killed (SIGKILL — not a graceful shutdown). The TUI must
remain responsive, display a clear error indicator, and offer a reconnection option
without losing the traffic history already captured.

This tests the system's resilience to unexpected server termination — one of the
most common real-world failure modes (FM-002).

## Setup

1. Start a mock MCP server that responds to `initialize`, `tools/list`, and periodically
   sends `notifications/message` (1 per second with incrementing counter)
2. Launch `forge-mcp tui`
3. Connect to the mock server from within TUI
4. Navigate to the traffic inspection panel
5. Wait until at least 10 messages are visible in the traffic log
6. From a separate terminal, kill the server process with `kill -9 <pid>`

## Steps

1. Observe TUI behavior immediately after server kill (within 1 second)
2. Attempt to scroll through previously captured traffic
3. Attempt to select and inspect a message detail view
4. Attempt to use keyboard shortcuts (quit, help, switch panels)
5. Look for reconnect option in the TUI
6. Restart the mock server process
7. Trigger reconnect from TUI
8. Verify new traffic begins flowing

## Expected Behavior

- TUI does NOT crash, hang, or produce a panic/stack trace
- Within 2 seconds of server death, TUI shows a clear error indicator:
  - Connection status changes to "disconnected" or "error"
  - An error message appears (e.g., "Server connection lost: <server-name>")
- Previously captured traffic remains scrollable and inspectable
- All keyboard shortcuts continue to work
- A reconnect action is available (keyboard shortcut or menu item)
- After server restart + reconnect, new traffic flows normally
- Traffic log shows the gap (disconnect/reconnect markers)

## Must-Pass Criteria

1. TUI process does not crash or become unresponsive after server SIGKILL
2. Error state is visually indicated within 3 seconds
3. Previously captured traffic is still accessible (scrollable, inspectable)
4. Keyboard navigation continues working in error state
5. Reconnection succeeds after server restart

## Satisfaction Scoring Rubric

| Criterion | 0 | 1 | 2 | 3 |
|-----------|---|---|---|---|
| TUI stability | TUI crashes or hangs | TUI stays alive but partially frozen | TUI responsive, minor rendering glitches | TUI fully responsive, no visual artifacts |
| Error indication | No error shown | Error in logs only, not visible in TUI | Error shown but unclear/delayed > 5s | Clear error within 2s with server name |
| Traffic preservation | Traffic history lost | Partial history, can't inspect details | Full history, minor scroll issues | Full history, detail inspection works perfectly |
| Keyboard responsiveness | Keys stop working | Some keys work, some don't | All keys work, slight delay | All keys work instantly, no degradation |
| Reconnection | No reconnect option | Manual reconnect requires restart | Reconnect option exists, works on retry | One-action reconnect, traffic resumes cleanly |
